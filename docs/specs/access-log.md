# 公開コンテンツのアクセスログ（#6703）

## 対象と方式

ライブラリ設定「ファイル処理詳細 → アクセスログを記録する」（`buildConfig.usingAccessLog`）が有効な場合、生成HTMLへ共通JSを自動挿入する。テンプレートに専用タグを追加する必要はない。公開資産は `assets/_astack/access-log/`。既定は無効。

初期実装はブラウザからAstackの収集APIへ直接送信する方式。公開サーバの認証連携キット、イベント画像による通知、Webサーバ/CDNのログ取り込みは含まない。将来の連携に備えて取得元、認証状態、認証情報の取得元を分けて保存する。

| イベント | 意味 |
| --- | --- |
| `FOLDER_VIEW` | フォルダ画面の表示 |
| `DOCUMENT_VIEW` | 文書画面の表示、または対応する標準ビューアでの表示成功・失敗 |
| `PRINT_REQUEST` | 印刷処理の開始要求。プリンタでの出力完了を意味しない |
| `DOWNLOAD_REQUEST` | ダウンロード要求。端末への保存完了を意味しない |
| `DOWNLOAD_TRANSFER` | 内蔵原本取得APIのサーバ転送結果。端末への保存完了を意味しない |

JSが動作しない直接ファイル取得や、未対応の外部ビューア内の操作は記録できない。ブラウザ通知は利用状況の記録であり、操作の実行を証明する監査証跡とは区別する。

## 有効化と公開

内部公開では既存の `/pub/{libraryName}/_api` を使う。API接続先は自動使用し、リバースプロキシ連携は内部/外部共通の任意設定とする。明示的に連携を有効にした場合だけ信頼する接続元を検証し、ユーザー名記録を有効にした場合だけプロキシが上書きしたヘッダーを履歴に利用する。未設定の内部公開で旧フラグを自動的に有効化せず、ブラウザからの未検証ヘッダーを信頼しない。リモート公開ではライブラリの「公開・配信 → 外部Webサーバ → APIパス」を優先し、空欄ならシステム設定 `publication.api-path` を継承する。公開先のブラウザから到達できるHTTP/HTTPSの接続先を設定する。HTTPS公開ではHTTPSのAPIを使い、公開先のCSPで収集先への接続を許可する。

有効化・接続先変更後は再ビルドが必要。HTML・標準ビューアの文書マニフェストへ対象情報を組み込む。無効化時は受付側でも現在の設定を確認し、古い公開HTMLからの送信を保存しない。

バックグラウンド／オンデマンド変換のマニフェストAPIは、最後に公開成功した設定に従って署名付き収集情報を応答へ付加する。TEMPLATEでの有効・無効切替は変換済み成果物を再変換せず反映し、保存した成果物自体は変更しない。応答は `Cache-Control: no-store` とする。公開ファイルだけで配信する場合・ログ無効の場合は収集情報を付加しない。

標準PDF・SVGビューアのアクセスログ対応版は `1.1.0` 以降。追加メタデータ・表示失敗通知の対応版は `1.2.0`。既存の固定バージョンを自動上書きしない。既存ライブラリでビューア内の操作を取得するには対応版を選択して再公開する。独自の画面内遷移・独自ビューアには共通JSへのイベント通知を追加する。

## 収集APIと信頼境界

`POST /pub/{libraryKey}/_api/access-events` にJSONを送る。通常の管理JWTや公開先のCookieを付けず、`credentials: omit` を指定する。

```json
{
  "schemaVersion": 1,
  "eventId": "f35d84ab-43e7-498a-b943-c366f4485cdf",
  "type": "PRINT_REQUEST",
  "occurredAt": "2026-10-25T01:00:00Z",
  "contextToken": "生成時に署名された対象情報",
  "sessionId": "fe0ab9b7-b530-44c4-96a7-eb0137e970bf",
  "result": "REQUESTED"
}
```

対象情報はサーバで署名し、別のライブラリ・任意のパスへの書き換えを防ぐ。ブラウザに配布する署名済み情報は秘密値でも閲覧権限でもない。取得した情報を使うイベントの捏造・再送を完全に防ぐ仕組みではなく、文書の配信・ACL認可にも流用しない。署名鍵はサーバの秘密領域に保持する。鍵だけの変更はDIFFの変更検知に含まれないため、変更後はFULLビルドで旧HTMLを再公開する。

ブラウザ由来のユーザ名・認証ヘッダーをユーザの証明として採用しない。API直接送信では内蔵公開も含め認証状態は `UNKNOWN`、アカウント名は未記録。前段の認証やWindows認証の利用者を推測しない。通信失敗を匿名アクセスに変更しない。ユーザ名の確認が必要な場合は後続の認証連携キットを使う。

収集APIだけに公開元を限定したCORSを適用し、管理APIや既存の公開取得APIの許可範囲を拡張しない。公開成功済みサイトのオリジンを照合する。CORSはブラウザの送信制御であり、送信者を認証する仕組みではない。

## 保存・再送・制限

メインDBの送信キューへの保存、または同一イベントの受付済みを確認すると `204` を返す。同じライブラリとイベントIDの組に一意制約を持ち、受付レシートを8日間保持して再送で件数を増やさない。OpenSearch登録後にDBの本文を削除しても、レシートのある再送は本文を再作成しない。表示や印刷・DLは受付の応答を待たずに継続する。ブラウザ側はメモリ内に最大64件、最大5分、各イベント最大5回の送信を試みる。要求の待機は最大8秒。localStorage等へ対象情報を残さず、画面終了後を含む永続的な配送保証はしない。

JSON本体は32KiBまで。ライブラリと接続元IPの組ごとに1分600件、レート制限のメモリ保持は最大4096組。逆プロキシ配下では実際に認識される接続元IPを確認し、必要に応じて外側でも制限する。制限はプロセス単位であり、分散レート制限ではない。イベント発生日時は受付時点の7日前から5分後まで。古い原本設定の署名情報は `409` で拒否する。4xx（429を除く）は再送を止める。

署名鍵の既定位置は `${astack.data-path}/secrets/access-log-context.key`。`astack.access-log.key-file` で変更できる。複数ノードを運用する場合は同じ署名鍵と履歴DBを使用し、バックアップは管理者のみに制限する。

受付ではイベント種別・日時・署名・対象との一致・ライブラリの有効状態を検査する。レート制限を設け、履歴へCookie・Authorization・閲覧URLのクエリ・フラグメントを保存しない。対象パスは生成時の相対パスを使用する。

### 開発用プロキシ経由のCORS

3000番のVite経由でも、収集APIのOPTIONS・POSTはバックエンドへ転送する。Viteの組み込みCORSは無効化し、公開成功済みサイトのOriginを許可する判定はバックエンドに集約する。ViteがOPTIONSへ先に応答すると、許可元であっても必要なヘッダーが欠けて送信できない。実運用のリバースプロキシもOPTIONSを転送し、Originを外部リクエストのまま保持する。任意のOriginや資格情報を一律に許可する設定は使わない。

### アクセス元IP

追加要望により、収集APIを受けたサーバの `HttpServletRequest.getRemoteAddr()` を `clientIp` として保存し、履歴とCSVに表示する。IPv4/IPv6に対応する。ブラウザにIP取得処理を追加せず、クライアントJSONの申告IPは採用しない。既存行はNULLとし、画面で「記録なし」と表示する。同一イベントの再送では最初の記録を上書きしない。

この値はサーバが確認した接続元であり、利用者本人・端末を一意に特定する情報ではない。NATやVPNでは共有アドレスになる。プロキシ経由で元IPを復元する設定がない場合は、プロキシのIPが記録される。開発用3000番のViteは、受けたソケットの接続元をX-Forwarded-Forへ設定する。利用者のForwardedとX-Forwarded-*はHTTP・WebSocketの入口で除去し、申告IPを引き継がない。開発プロファイルはTomcatのNATIVE方式で、127.0.0.1とIPv6ループバックのプロキシだけを信頼する。LANから8080番への直通で送られた偽のヘッダーは採用しない。Viteをさらに別のプロキシの背後へ置く場合は、その構成に合わせた信頼境界の再設計が必要。

アプリ独自の処理で `X-Forwarded-For` の先頭値を採用しない。導入先で元IPを復元する場合は、信頼するプロキシを明示し、プロキシが実際の接続元を正しく追加または上書きすることを確認したうえで、Spring Boot/Tomcatの標準機能を使う。代表的な設定は `server.forward-headers-strategy=NATIVE` と `server.tomcat.remoteip.internal-proxies`。全プロキシを信頼する設定は使わず、外部からのバックエンドへの直通も制御する。本番用の既定設定を一律には変更しない。開発プロファイルのループバック限定設定を、別ホストのプロキシへそのまま流用しない。取得済みのループバックIPから、過去の実接続元IPを復元することはできない。

参照: [Spring Bootのプロキシ設定](https://docs.spring.io/spring-boot/3.5/how-to/webserver.html#howto.webserver.use-behind-a-proxy-server)、[X-Forwarded-Forの信頼境界](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/X-Forwarded-For)。

### 閲覧・処理のメタデータ

- `sessionId`: 公開先・API接続先単位で生成したランダムUUID。タブ内のsessionStorageでページ遷移・再読み込みをまたいで保持し、ストレージが使用できない場合はメモリ内で保持する。利用者本人を識別する値ではない。イベントの再送UUIDとは別。
- `documentVersion`: 署名済み対象情報に含む公開元文書のSHA256。前回の変換成果物を継続公開する場合は、その保存版のハッシュを使う。版が確認できない場合・フォルダ・最新原本の直接取得では未記録。ブラウザの任意申告は採用しない。
- `browserName` / `browserVersion` / `osName`: 受付時のUser-Agentから既知のブラウザ名・メジャー版・OS名だけを分類する。生のUser-Agentは保存しない。自己申告に基づく参考情報。
- `result`: `OBSERVED`（画面表示）、`REQUESTED`（印刷/DL要求）、`SUCCEEDED`（文書読み込みまたはサーバ転送成功）、`FAILED`（確認可能な失敗）。実際の印刷完了・端末保存完了は取得しない。
- `failureCode`: 固定コードのみ。文書表示の `DOCUMENT_LOAD_FAILED` / `RENDER_FAILED`、サーバ転送の `SOURCE_NOT_FOUND` / `SOURCE_UNAVAILABLE` / `TRANSFER_FAILED`。例外本文・接続資格情報は保存しない。

ブラウザ送信から `DOWNLOAD_TRANSFER` は作成できない。原本取得APIは認証・ACL・公開設定を確認後のGET転送だけを記録し、HEADは除く。記録の障害は原本取得を失敗させない。リモートWebサーバ上の静的ファイルの転送結果は、将来のログ連携の対象とする。

旧SDK・旧署名情報・既存履歴も受け付け、取得できない新項目は未記録とする。セッション・文書版の取得には再ビルド・再公開が必要。対応ビューアの成功・失敗通知には `1.2.0` を選択する。

### 保存件数と保持期間

履歴はOpenSearchの専用月別インデックスへ保存する。メインDBは未送信本文と短期の受付レシートを保持し、OpenSearchへの個別登録成功を確認した本文だけを削除する。既存DBの履歴も同じ経路で移行する。ビルドDB再作成から分離する。ライブラリ名・対象パスはイベント時点の値として保持し、ライブラリ削除で連鎖削除しない。保存総件数にアプリ固有の固定上限はなく、上限到達による古い行の件数削除もしない。CSVの1回10000件・一覧の1ページ最大100件は保存件数の上限ではない。利用可能なディスク容量、未送信キュー・インデックスの大きさ、検索条件、バックアップ・復旧時間によって実用容量は変わる。大規模長期負荷の保証件数は未測定。

管理画面の「保存期間」で全ライブラリ共通の保持日数を0〜3650日で設定できる。既定0は無期限（自動削除なし）。設定変更だけでは削除せず、起動1時間後から毎時、OpenSearchで受付日時が期限より古いイベントを1回最大10000件削除する。期限の境界時刻のイベントは保持し、検索基盤の障害時はその実行を中断する。DBの未送信本文は保持日数にかかわらず削除しない。受付レシートは8日経過後に整理するが、未送信本文に対応するものは保持する。大量の期限切れ履歴は複数回に分けて削除するため、設定日数を超えて残る場合がある。総件数・最古/最新の受付日時はOpenSearchに反映済みの履歴を設定APIで確認できる。削除した履歴の復旧にはバックアップが必要で、移行済み履歴にはOpenSearchスナップショットも必要。

## 管理画面と管理API

管理者だけが「アクセス履歴」を利用できる。一覧・CSV・保存件数はOpenSearchを検索する。画面には「アクセス履歴への反映には時間がかかる場合があります。」と表示し、受付直後の可視性は保証しない。検索基盤を利用できない場合は503を返し、DBへの自動切替や0件扱いはしない。ライブラリID、操作、相対パス、セッションID、結果、受付日時の期間で検索・ページ送りし、CSVで取得する。発生日時はブラウザ申告、受付日時はサーバ時刻として区別する。

| API | 内容 |
| --- | --- |
| `GET /api/access-events` | `libraryId`、`type`、`path`、`from`、`to`、`sessionId`（UUID）、`result`、`page`（0始まり）、`size`（既定25、最大100） |
| `GET /api/access-events/export` | 同じ検索条件でCSV。最大10000件、超過時は条件を絞るようエラーを返す |
| `GET /api/access-events/settings` | 保持日数、総件数、最古/最新の受付日時、CSV上限 |
| `PUT /api/access-events/settings` | `{ "retentionDays": 0 }` の形式で保持日数を設定（ADMIN限定） |

管理APIとCSVには `Cache-Control: no-store` を付ける。CSVのセルには式として解釈される文字列の対策を行う。

## 導入確認

- 専用の検証ライブラリで有効化・再ビルドし、フォルダ・文書・印刷要求・DL要求を履歴と照合する。
- リモート公開はブラウザからAPIへ疎通し、許可元のCORSと不許可元の拒否を確認する。
- 送信失敗が閲覧を妨げず、再送しても重複しないことを確認する。
- ログ設定無効化、ライブラリのゴミ箱移動、一般ユーザからの履歴API要求が保存・閲覧を許可しないことを確認する。
- 既存ビューア、カスタムテンプレート・CSP、外部認証付き公開の互換性は導入環境で確認する。

保存構成・インデックス定義・移行と運用は [OpenSearch連携設計](access-log-opensearch.md) を参照。

### アクセス履歴の一覧表示

「アクセス履歴」はサイドバーの「システム管理」に配置し、管理者だけに表示する。画面・履歴取得・CSV出力の管理者限定の権限制御を維持する。

一覧は操作日時、ライブラリ名、操作、対象パス、ユーザー、アクセス元IP、詳細の7列とする。ライブラリIDと受付日時は表示せず、不明な認証状態は「不明」と表示する。対象パスは先頭に `/` を付け、長い場合は省略する。全体はホバー時または詳細画面で確認できる。操作結果の意味や保存・CSV出力の説明はツールチップにまとめ、反映に時間差がある旨は常時表示する。保存値・CSV・検索条件・並び順は変更しない。

認証リバースプロキシによるユーザー識別と接続元制限は [公開APIの接続元制限と認証ユーザー連携](publication-api-security.md) を参照。認証連携ONの同一オリジン中継ではSDK版3が認証情報を利用し、信頼した経路からのみユーザー名を記録する。
