# AI処理・プロバイダ・ベクトル索引

確認基準は [索引](../README.md) を参照。

## 機能別設定と入力

ライブラリの `aiProcessingConfig` は全体の `enabled` と、要約・タグ・メタ情報・ベクトルの個別有効化を持つ。共通接続・LLMを継承し、機能ごとに接続・モデルを上書きできる。タグとメタ情報は `ORIGINAL` または `SUMMARY` を入力にする。

要約入力には要約機能が必要で、対象ジョブでも依存処理として要約を含める。実行時の要約失敗で元文書へ自動切替しない。画面上で要約機能を無効にする際は入力選択を元文書へ戻す。実行対象はライブラリの有効機能とジョブ選択の組合せで決まり、開始時の設定スナップショットを使う。

`summaryRequirements`、`tagRequirements`、`metaInfoRequirements` は各4000文字以内の生成プロンプト。空欄保存は標準文へ補完する。`GET /api/ai-prompts/defaults` と実行時は同じローダーを使用する。外部 `data/prompts/` の `summary`・`keyword`・`semantic` の `-system.md` と `-requirements.md` を優先し、未配置ならパッケージ内の標準を使う。システム指示とユーザメッセージを分離する。

設定変更は次回生成に適用する。原本が同一で生成済みの要約・タグ・メタ情報を、モデルやプロンプト変更だけで通常ジョブが作り直すことはない。既存結果へ反映するには強制再生成を使う。生成保存時は入力索引の版、HTML参照時は公開する原本の版との対応を確認する。検索インデックス単独実行で公開物より新しい原本を抽出した場合、AIはその索引版を利用する。公開物との一時的な版の差は許容し、古い索引版のAI結果は採用しない。

## 本文抽出・索引と公開検索の分離（#6806）

AI処理が有効なライブラリは、検索なし・外部検索を選択していても原本本文を抽出し、AI入力用のOpenSearch索引を作成する。AIを有効化して保存・インポートすると `searchConfig.enableCreateIndex` も有効にする。既存のAI有効設定は、保存値がOFFでも共通の実行判定で索引作成を有効として扱う。検索方式は変更しない。本文の準備後にAIを実行し、設定の保存だけではAIジョブを予約しない。既存文書に適用する場合はビルドまたは検索インデックス作成を実行する。

公開ページに検索を表示するかは `searchConfig.showOnPublishedPages` で独立して選ぶ。OFFでも管理画面の検索、本文抽出、AI処理は停止しない。検索なしの場合と独立配信の場合は、表示設定がONでも公開ページへ検索導線を出さない。未指定は従来の検索設定による表示を継承する。公開ページへの反映はHTML再生成で行い、表示の切替で索引や生成済みAI情報を削除しない。表示設定は検索APIへのアクセス許可を変更しない。

| 検索方式 | AI | 本文抽出・内部索引 |
| --- | --- | --- |
| 検索なし | OFF | 作成しない |
| 検索なし | ON | AI用に作成する |
| 内部検索 | OFF / ON | 作成する（通常の索引作成設定） |
| 外部検索 | OFF | 作成しない |
| 外部検索 | ON | AI用に作成する。検索先は外部のまま |

## 生成と検索利用の分離（#6767）

AI処理・要約生成は概要検索の、AI処理・ベクトル生成は意味検索の前提条件とする。検索利用のON/OFFは `searchConfig.elasticPreface` / `semanticEnabled` で管理し、生成機能のONだけで検索利用をONにしない。前提条件OFF時はフォーム上で対応する検索設定もOFFにし、保存・インポートでの不整合を拒否する。意味検索OFFでもベクトル生成と既存ベクトルを保持する。検索時のクエリ埋め込みは意味検索が利用可能な場合だけ行う。

設定の有効化とデータ準備完了を区別し、既存文書への適用にはAI処理を実行する。モデル・接続・粒度の変更による再構築中は、従来どおり利用可能な旧索引を保持する。詳細は [検索仕様](search-and-viewing.md) を参照。

## 予約と実行枠

`POST /api/ai-jobs/reserve` は `libraryId` と実行オプションを受け付ける。オプションは `generateSummary`、`generateSearchTags`、`generateMetaInfo`、`generateVector`（既定true）、`forceRebuild`（既定false）。一覧・詳細・retry・cancel・ログダウンロード・SSEログ配信を提供する。

文書単位のAI処理ログには`fileId`と`sourcePath`（原本のフルパス）を併記する。`sourcePath`は原本ストレージの表示用ルート、ライブラリの元文書パス、入力索引内の相対パスから組み立て、原本への接続・存在確認は行わない。認証情報を含めず、改行・引用符等はJSON文字列としてエスケープする。変換後ファイルや一時抽出本文のパスは使用しない。ルートを解決できない場合もAI処理は続行し、`(原本ルート不明)/相対パス`を記録する。部分失敗の概要とベクトル索引切替時の文書エラーにも原本パスを含める。既存のログは書き換えず、反映後に実行したジョブから適用する。

同一ライブラリの待機ジョブは作成日時・ID順に開始する。異なるライブラリは全体枠 `ai.processing.concurrency`（既定4）と各接続の `maxConcurrentJobs`（1〜64、既定1）の範囲で並列実行する。使用する副接続も枠に含む。RUNNINGとCANCEL_REQUESTEDは枠を保持し、WAITINGは保持しない。

`AiJobAdmissionService` は単一バックエンドプロセスを前提に開始判定からコミットまでを直列化し、ライブラリ・接続・ジョブのDBロックを使用する。複数接続はID順に取得する。接続設定が異なるAPIキーの共通契約枠は自動検出しない。

## プロバイダとモデル

登録種別は `BEDROCK`、`OPENAI`、`VERTEX_AI`、`OPENAI_COMPATIBLE`、`GEMINI`。管理接続とLLM/EMBEDDINGモデルは分離する。モデル候補取得、接続内の既定モデル、機能別選択を提供する。種別登録だけで任意モデル・任意APIへの接続を保証するものではない。

### 接続ごとの再試行・ストリーミング

管理画面「AIプロバイダ」の接続編集で、全プロバイダに共通して次の項目を設定する。APIでは接続の `settings` 内に保存する。機能別に別の接続を指定した場合は、その接続の設定を使う。

| 項目 | 画面の新規登録時の既定値 | 範囲・意味 |
| --- | --- | --- |
| `retryPolicy.maxAttempts` | 3 | 初回を含む最大試行回数、1〜100。1なら再試行しない |
| `retryPolicy.initialBackoffMs` | 1000 | 最初の再試行待機時間、0〜3600000ms |
| `retryPolicy.maxBackoffMs` | 10000 | 倍増する待機時間の上限。初期待機時間以上、3600000ms以下 |
| `retryPolicy.jitterRatio` | 0.2 | 待機時間へ加算するランダム比率、0〜1 |
| `stream` | false | trueならAIサービスから逐次受信、falseなら従来の一括受信 |

再試行はAIジョブの要約・タグ・メタ情報・ファイル／ページ埋め込み・タグ辞書整理に適用する。既存の再試行可能なエラー分類を維持し、認証などの恒久エラーを繰り返さない。入力長超過の自動短縮は別の既存上限を維持する。待機時間は2倍ずつ増え、例外に再試行待機時間の指定がある場合は長い方を採用し、その後ジッターを加算する。従ってAPI指定待機時間やジッターを含む実際の待機は `maxBackoffMs` を超えることがある。

既存接続のJSONに `retryPolicy` がない場合は従来の `ai.processing.retry-*` を継承し、取得APIにもその有効値を返す。取得だけではDBを書き換えない。画面で保存すると接続別の値として保存され、以後はグローバル値より優先する。APIの部分更新で `retryPolicy` / `stream` を省略した場合は既存値を保持し、`retryPolicy` を指定する場合は4項目をまとめて送る。新規API登録で省略した場合の再試行値も従来のグローバル値を使う。`stream` が未設定の既存接続はfalseとして動作する。

ストリーミングはバックエンドとAIサービス間の受信方式であり、管理画面へ回答を逐次表示する機能ではない。要約・タグ・メタ情報・タグ辞書整理で使用し、埋め込みは一括応答を維持する。

| プロバイダ | stream=trueの呼び出し |
| --- | --- |
| OpenAI / OpenAI互換 | Chat Completionsの `stream: true` とSSE。`stream_options.include_usage: true` で最終使用量を取得 |
| Gemini | `streamGenerateContent?alt=sse` |
| Vertex AI | Google Geminiの `streamGenerateContent?alt=sse` |
| Bedrock | AWS SDKの `ConverseStream`。構造化出力のツール入力JSONも差分を連結 |

Bedrockのストリーミングには対象モデルに対する `bedrock:InvokeModelWithResponseStream` 権限が必要。アプリケーションからIAM権限は変更しない。

完了を確認してから回答と使用量を既存の後続処理へ渡す。途中切断・不正JSON・出力上限・安全性による停止を正常完了として保存しない。未対応の接続先やモデルが拒否した場合も非ストリーミングへ黙って切り替えない。OpenAI互換サーバーは上記のSSE形式とusageオプションに対応している必要がある。受信中にもキャンセルを確認するが、HTTPでデータが届かない間の検出は読み取りタイムアウトに制約される。

接続の `timeoutMs`（既定30000ms）はOpenAI・OpenAI互換・Gemini・Vertex AIの生成／埋め込み呼び出しに接続・読み取りタイムアウトとして適用する。ストリーミングでは読み取りの無通信時間の上限であり、回答全体の総時間ではない。Bedrockは従来どおりSDKのAPI呼び出し・試行全体の上限に適用する。Vertex AIは1〜600000ms、その他は1〜3600000ms。プロキシやAIサービス側の504の上限は別設定であり、この設定では変更しない。

追加設定は既存の接続設定JSONに保存し、DBスキーマの変更は不要。導入前に管理DBをバックアップする。旧版へ戻す場合は、旧版が追加JSON項目を読めない可能性があるため、保存前の接続設定を復元するなど追加項目を取り除いてから戻す。外部AIサービスとの実接続試験は未実施で、ローカルHTTPサーバーとSDKの模擬応答で検証している。

### Bedrock

BedrockはAWS SDKのConverse/ConverseStream/InvokeModelを利用する。既定認証チェーンまたは明示資格情報、リージョン、モデル別設定を管理し、認証情報をマスク・暗号化する。設定保存時と実行直前の能力検証を共通化する。

| Bedrockの実装済み系列 | 処理 |
| --- | --- |
| Claude Haiku / Sonnet 4.5、Nova Micro / Lite / Pro V1 | 生成 |
| Titan Text Embeddings V2 | 埋め込み、256/512/1024次元 |
| Cohere Embed v3 | 埋め込み、1024次元 |
| Cohere Embed v4 | 埋め込み、256/512/1024/1536次元 |

この表はリポジトリの能力定義であり、AWSで現在提供される全モデルの一覧ではない。未対応キー・組合せ・系列を拒否し、Claudeのtemperature/topP排他やthinking制約も検証する。過去のBedrock検証記録はAWS実接続未実施と明記しており、今回も外部接続試験を行っていない。

## ベクトル再構築と公開

本文・要約等の索引とベクトル索引を分離し、ライブラリとモデルに対応する物理索引・アクティブ状態を管理する。モデルや埋め込み設定の変更は別の物理索引へ再構築し、全量成功後にエイリアスと状態を切り替える。再構築中・失敗時は旧検索を維持し、要約・タグ・メタ情報を削除しない。クエリ埋め込みもアクティブモデル・設定・物理索引の組を使用する。

AI入力には検索索引に登録済みの抽出本文を使用する。原本を再抽出せず、原本snapshot・容量・更新日時・ハッシュや抽出タスクとの再照合を実行条件にしない。実行前、要約・ベクトルの保存前、ベクトル索引の切替前に、現在の本文索引の存在・入力索引版（`file.indexed_source_revision`）・ACLを照合する。処理中に索引が更新・削除された場合は旧結果を保存しない。版IDのない旧索引では索引内のパス・容量・更新日時・ハッシュを比較する。原本だけが変更・アクセス不能になっても、索引が同じならAI処理を継続する。原本の変更は次回の索引更新で反映する。

公開停止・削除・アクセス権変更の確認は引き続き現在の公開管理情報・文書設定・ACLで行い、原本の内容照合と分離する。この管理情報の読取中だけ管理DBトランザクションを中断し、確認後に復帰する。待機中AIは最新の索引ジョブ完了を待つ。実行中AIはFULL/DIFFビルド開始・公開世代・索引ジョブIDの変更だけでは中止しない。文書の保存時は本文索引更新と共通のライブラリ行ロック内で、OpenSearchのrealtime GETによる本文版・ACLと現在の公開権限を再照合する。更新・削除された文書は部分失敗として旧結果を破棄し、残りの文書を継続する。次の索引更新後のAIでは、本文版とAI設定が同じ処理済み成果を再利用する。

索引確定時は管理DBのジョブ行ロックで明示的キャンセルと直列化する。ベクトル索引の全体切替はライブラリ行ロック内で本文索引をrefreshし、開始時の有効文書集合・索引内の文書集合・全対象の本文版と公開権限を照合してから行う。全量成功時だけ切り替え、失敗時は旧検索を維持する。

AI成功結果は後続TEMPLATEでHTMLへ反映する。通常のHTML公開をAI待ちにせず、TEMPLATEからAIを再予約して循環させない。詳細は [ジョブ・公開](jobs-and-publication.md) を参照。

## 検索タグの辞書整理と補正

タグは辞書を使わずに生成し、`tags.raw_ai` と検索用の `tags.ai` に保存する。同じ原本の初期タグは `original_ai` に保持する。辞書補正は毎回元タグから計算し、未知タグ・手動タグを消さない。複合タグは機械的に分割せず本文からの再生成が必要な保留とする。

### 共通・共有・固有辞書

全ライブラリへ適用する共通辞書、複数ライブラリへ参照で割り当てる共有辞書、ライブラリ固有辞書を組み合わせる。同じ別名に複数の標準名が対応する場合はすべて付与し、重複を除去する。標準名は辞書内で一意、別名は複数項目に登録可能。大小文字・区切り記号・部分一致による自動統合はしない。

ライブラリ一覧の「検索タグの整理」から管理する。辞書選択、共有辞書の作成・複製・割当、辞書の編集と過去版の復元に対応する。登録・利用設定の編集は共通モーダルを使う。共通辞書と固有辞書は常に適用し、共有辞書はライブラリごとに最大30件割り当てる。辞書は5000項目、標準名100文字・意味500文字・別名は各100文字で50件以内。

既存 `tag_dictionary_revision.library_id` の正の値は従来どおり固有辞書として保持し、0は共通、負のIDは共有辞書に使う。既存の版・整理案は移動や削除をしない。`tag_dictionary_scope` に共有辞書の定義、`tag_dictionary_settings` にライブラリごとの設定を保持する。各版は追記保存し、保存時に現在版を照合して同時編集を上書きしない。

### 新規タグだけの差分整理

選択した辞書の対象ライブラリから元タグを集計し、ライブラリ別文書数と代表文書を残す。共通辞書は全文書、共有辞書は割当先、固有辞書はそのライブラリを集計する。既存辞書の標準名・別名と完全一致するタグ、および同じ辞書で判定済み・保留のタグはAI入力から除外する。共有辞書で整理済みなら別の割当先でも再処理しない。

AIは1回最大30の新規タグを、既存概念への別名追加（MATCH）・新概念登録（NEW）・保留（HOLD）に分類する。既存の標準名・意味は変更せず、決定に使われなかった新規項目や勝手な別名は保存しない。全候補の判定を検証し、辞書の追加分・判定履歴・結果を同じトランザクションで保存する。辞書全体の再生成はしない。代表文書はライブラリの偏りを避けて取得し、AI入力は最大3文書の抜粋を使用する。要約がない文書は先頭ページの本文を補う。辞書が200項目を超える場合は表記の近い200項目を参照候補にする。この候補選択や代表文書だけで、すべての同義語を発見できることは保証しない。

`tag_dictionary_decision` に辞書ごとの元タグ・判定・標準名・理由・ジョブIDを記録する。通常の追加更新では判定履歴を失効させない。削除した別名や、削除・意味変更した標準名に関連する判定だけを再評価可能にする。保留タグは画面で選択して再評価できる。100文字を超える元タグは残すが自動整理から除外する。

「未整理タグをまとめて整理」は最大30件ずつのAIジョブを連続予約し、未整理がなくなれば終了する。既存のAI接続枠・設定スナップショット・キャンセル・使用量記録を使う。整理専用ジョブでは公開用TEMPLATEを予約しない。外部API失敗・競合・キャンセルは処理状態を失敗として保存し、無制限の再試行をせず画面から再実行する。

### 自動整理・自動補正

ライブラリごとの「タグ生成後の差分整理」と「タグの自動補正」は既定ON。新規タグの登録先は既定で共通辞書とし、利用中の共有・固有辞書を選択できる。既存データは配置直後に自動でAIへ送らず、通常のタグ生成成功後、または管理画面からの予約で整理を開始する。

辞書更新・割当変更・タグ生成後に、自動反映が有効なライブラリの補正要求を `tag_dictionary_work` に永続化する。補正中に追加要求が来ても失わず、再起動で中断した補正は再開する。自動処理は通常15秒間隔で確認する。手動反映では辞書更新だけを保存し、補正プレビュー後に適用する。辞書整理と補正それぞれの状態・補正件数・競合・失敗を画面へ表示し、再実行できる。

補正プレビューは最大100文書の変更前後を表示する。適用辞書の組合せ・各版・文書更新番号から作ったフィンガープリントを照合し、索引の楽観ロックで文書更新との競合を防ぐ。手動タグ・要約・メタ情報・ベクトルを保持する部分更新を行い、使用辞書の版を `dictionary_sources` に記録する。元タグへの復元にもプレビューを使う。検索へは適用後に反映し、公開済み文書一覧へは次回ビルドで反映する。1ライブラリ5万文書以内を対象とする。

管理APIは `/api/tag-dictionaries` の一覧/共有辞書作成、`/{id}` のGET/PUT、`/{id}/inventory`・`/history`・`/history/{revision}`・`/decisions` のGET、`/{id}/organize`・`/reset-decisions` のPOST。`/libraries/{libraryId}/settings` で利用設定をGET/PUTし、`/work` で状態、`/libraries/{libraryId}/reflect` で自動補正の再実行を扱う。管理者専用。従来の `/api/libraries/{libraryId}/tag-dictionary` は固有辞書の互換APIとして残す。補正プレビューと適用・結果取得には従来のライブラリAPIを使用する。スケジュールから整理専用オプションを直接予約することは許可せず、この画面と内部の差分整理要求を使う。

## AIの定時実行

ジョブ管理のスケジュールで処理の種類に「AI処理」を選び、ライブラリ（またはプロジェクト配下全体）と実行オプションを指定する。重複時の動作はスケジュールごとに「重複時は追加しない」（既定）と「毎回予約する」を選ぶ。同じライブラリ・同じ5つの実行オプションを持つ待機中・実行中・停止要求中ジョブを対象に判定する。手動予約・再実行・スケジュールの即時実行は追加予約を受け付ける。接続別の枠と同一ライブラリFIFOは既存の開始判定を使う。詳しくは [ジョブ・ビルド・公開](jobs-and-publication.md) を参照。

## 使用量・概算コスト（#6783）

AIプロバイダ設定の操作から接続別の使用量・概算コストを確認する。ジョブと検索の各API呼び出しを管理DBへ記録し、料金履歴、期間集計、明細、CSVを提供する。欠落した使用量を0とせず、通貨・未算定・不明を区別する。詳細は[AI使用量・概算コスト](ai-usage.md)を参照。
