# ジョブ・ビルド・公開

ジョブ管理のタブは「ビルド」「ファイル変換」「検索インデックス」「AI処理」「スケジュール」の順で表示する。ファイル変換とスケジュールは管理者に表示し、一般ユーザーには従来どおり利用可能なタブだけを表示する。

確認基準は [索引](../README.md) を参照。

## モードと処理経路

| モード | 原本走査・変換 | HTML生成・公開 | AI |
| --- | --- | --- | --- |
| `FULL` | 全体を走査し全件を変換対象へ戻す（省略設定は適用） | 実行 | 設定に応じ後続予約 |
| `DIFF` | 差分検出し必要な変換を実行 | 変更をマージ、削除対象を整理 | 設定に応じ後続予約 |
| `TEMPLATE` | 実行しない | 保存済み成果物から再生成・公開 | 予約しない |

実行モードはジョブの `mode` に一本化する（[#6725](https://developer.astack.jp/redmine/issues/6725)）。手動予約・スケジュールのモードを使用し、再実行もジョブに記録されたモードを使用する。FULLは全件、DIFFは差分、TEMPLATEはHTML再生成とする。失敗・取消・複数予約でも、各ジョブに保存されたモードを変更しない。次回だけ全件にする場合はFULLジョブを明示的に予約し、定期的に全件にする場合はスケジュールをFULLに設定する。

ライブラリの旧 `fileDiff`・`allContentsOnNext`・`buildAllEverytime` は実行処理へ接続されていなかったため、設定画面の選択肢を廃止する。API・JSON・インポートは互換性のため従来の保存値を受け付けるが、実行モードへ適用せず、自動消費・リセットもしない。従来の同時ON正規化（毎回全件を優先）は保存互換性として維持する。暗黙の予約作成や既存予約の書換えは行わない。`fileDiffDuration` は新規・更新マークの期間設定として継続し、差分対象の選択には使わない。

FULLは既存データを無条件で全削除するモードではない。パスで文書IDを維持し、原本が変わらないAI情報を保持する。原本変更・削除時は対応するAI情報を無効化する。

クロール、閲覧用変換、フォルダ完了判定、HTML生成、公開をビルドで処理する。原本本文の抽出と検索索引への登録は、ビルドとAIから独立した「検索インデックス」ジョブで行う。FULL/DIFFの正常完了後に検索索引が有効な場合だけ自動予約し、AIは対応する索引ジョブの完了を待つ。HTML公開は索引作成やAI完了を待たず、索引の失敗で公開済みHTMLを巻き戻さない。AI終了時のHTML反映要求は `JobFollowup` に永続化し、後続TEMPLATEで反映する。起点ジョブと処理対象の版で重複・旧世代への後続実行を防ぐ。失敗・キャンセルを無限自動再試行せず、履歴と明示的再実行で扱う。

## 検索インデックスジョブ（#6805）

ジョブ管理の「検索インデックス」タブで、ライブラリ・元ビルド・状態・進捗・対象/処理済み/失敗/スキップ件数・開始/終了日時を管理する。原本の本文抽出、チャンク化、ファイル情報・ACL・本文の検索索引登録を含む。AIの要約・タグ・ベクトル生成はこのジョブに含めない。AIが無効でも内部検索が有効なら作成する。

3つの閲覧用変換方式で共通の流れを使用する。バックグラウンド変換の完了やオンデマンドの初回閲覧を待たない。TEMPLATEは索引作成を予約せず、AI反映による循環を作らない。

元ビルドID、公開時の文書版、実際に抽出した最新原本の版を記録する。索引単独実行では公開時から更新された原本も処理し、公開物との一時的な差を許容する。ビルド用情報を索引から更新せず、次回DIFFと索引処理で一致させる。同じライブラリの索引処理は直列化し、新しい公開世代へ進んだ場合は古い対象やAI後続要求をそのまま適用しない。再実行は履歴を上書きせず、新しいジョブとして記録する。本文抽出の詳細と対象形式は [原本本文抽出仕様](source-text-extraction.md) を参照。

全件成功はSUCCESS、非対応・対象外または一部の失敗を含む完了はWARNING、全件の抽出失敗やジョブ自体の異常はFAILEDとする。SUCCESS/WARNINGでは利用可能な本文をAIへ渡し、FAILEDでは自動AIを開始しない。最新公開世代のWARNING/FAILED/CANCELLEDだけを再試行でき、READYの文書は再利用する。

AIの起点には索引ジョブIDを保存する。索引完了状態と後続AI要求を同じトランザクションで確定し、再起動の境界で予約を失わない。AI開始時は最新の索引ジョブの準備完了を確認する。実行中AIはビルド開始や索引ジョブ世代変更だけでは中止せず、文書単位で入力本文版・公開状態・ACLを保存直前に共通ライブラリロック内で照合する。更新・削除された文書だけ旧結果を破棄し、残りを継続する。本文版とAI設定が同じ成果は後続AIで再利用し、ベクトル全体切替時は文書集合と全本文版の一致も確認する。既存環境の導入前ビルドを一斉再索引化せず、旧タスク・待機AIは既存の準備条件で継続する。

## ACP変換の事前チェック

ACP実変換が必要なFULL/DIFFは、予約時と実行開始時にライセンス権限を検査する。権限不足時は予約を拒否し、スケジュールは失敗ジョブを記録する。予約後の権限喪失は開始前の検査でFAILEDにする。実行中の権限不足もFAILEDで終了し、公開せず既存公開物を維持する。画面とログに「ACP変換が必要ですが、登録ライセンスにACPの利用権限がありません」と理由を示す。判定対象・変換不要時の例外は[ライセンス仕様](licensing.md)を参照。権限回復後の再実行は明示的に行う。

## 状態、予約、排他

| 種別 | 実装の状態 |
| --- | --- |
| ビルド | `WAITING`、`RUNNING`、`SUCCESS`、`WARNING`、`FAILED`、`CANCELLED` |
| 検索インデックス | `WAITING`、`RUNNING`、`SUCCESS`、`WARNING`、`FAILED`、`CANCELLED` |
| AI | `WAITING`、`RUNNING`、`CANCEL_REQUESTED`、`SUCCESS`、`FAILED`、`CANCELLED` |

ビルドの手動予約・再実行は、同一ライブラリにWAITING/RUNNINGがあっても新しいWAITINGジョブとして受け付ける。実行候補は優先度の昇順、作成日時の昇順で取得し、同一ライブラリのビルドは直列に開始する。待機中ジョブの取消は先行する実行中ジョブを停止しない。AIも同一ライブラリへの追加予約を受け付け、開始は直列にする。ビルドワーカーの全体並列度の既定は2、AIの既定は4。ビルド開始時にもライブラリをロックして実行状態を再検査し、RUNNINGのコミット後に非同期ワーカーを起動する。

予約要求は対象の `projectId` または `libraryId`、`mode`、`priority`（1〜10、既定5）、任意の `params` を持つ。APIの代表例は次のとおり。

| API | 用途 |
| --- | --- |
| `POST /api/builds/reserve` | ビルド予約、201 |
| `GET /api/builds`、`GET /api/builds/{jobId}` | 一覧・詳細 |
| `POST /api/builds/{jobId}/cancel`、`/{jobId}/retry` | キャンセル・新ジョブで再実行 |
| `GET /api/builds/{jobId}/task`、`/{jobId}/history` | 進捗・変換履歴 |
| `GET /api/index-jobs`、`/{id}` | 検索インデックス作成の一覧・詳細・文書別結果 |
| `GET /api/index-jobs/{id}/log` | 検索インデックス処理ログの表示・全文ダウンロード（`download=true`） |
| `POST /api/index-jobs/reserve`、`/{id}/retry` | 索引のみを新しいジョブとして予約・再実行 |
| `GET/POST /api/schedules`、`PUT/DELETE /api/schedules/{id}` | Cronスケジュール管理 |
| `POST /api/schedules/{id}/run` | 操作ユーザーで即時実行 |

スケジュールはCron、タイムゾーン、有効期間、有効フラグ、対象、処理の種類（BUILD／AI）、ビルドモードまたはAI実行オプションを保持する。現在の管理APIは管理者制限を受ける。

スケジュールの `duplicatePolicy` は定時実行での重複時の動作を表す。`SKIP_DUPLICATES`（重複時は追加しない、既定）は、ライブラリ行ロック内で同一ライブラリ・同一モードにWAITING/RUNNINGがある対象だけをスキップする。`QUEUE_EVERY_RUN`（毎回予約する）は新しい待機ジョブを追加する。プロジェクト一括実行では対象ごとに判定する。全対象をスキップした場合もlastRunAtを更新して正常終了し、次回時刻へ進む。手動予約・再実行およびスケジュール画面の即時実行は、この設定にかかわらず待機ジョブを追加し、同一ライブラリの実行を直列化する。既存の待機ジョブは削除・吸収しない。

AIの定時実行も同じ `duplicatePolicy` を使う。同一ライブラリで要約・タグ・メタ情報・ベクトル生成・強制再生成の5つの実行オプションが一致するWAITING/RUNNING/CANCEL_REQUESTEDを重複とみなし、JSONの項目順や省略された既定値で区別しない。ビルドとAIは別種のジョブとして判定し、各種別の同一ライブラリ内で既存の直列実行を維持する。AI接続・モデルは既存方式に従い実行開始時のライブラリ設定を使う。ビルド後の内部自動AI連携とAI完了後のHTML反映は既存の集約・後続予約を維持する。

既存行と処理の種類を省略した登録はBUILDとして扱い、既存行と重複設定を省略した新規登録は `SKIP_DUPLICATES` を使う。AIスケジュールの登録はビルドモードを省略でき、`aiOptions` 未指定時は通常のAI既定値を使う。ビルドはmode必須。処理の種類・重複設定・AIオプションを省略した更新は、保存済みの該当設定を維持する。即時実行APIはビルドなら従来のBuildJobResponse、AIならAiJobResponseを201で返す。`ddl-auto=validate` の環境は [スキーマ更新SQL](../migrations/6736-schedule-duplicate-policy.sql) を先に適用する。

管理者向け互換API `/api/build/libraries/{libraryId}/start`・`/stop`・`/progress` も残り、開始は予約Serviceへ委譲する。GET progressはADMIN/USERの対象ライブラリ認可を受ける。旧設計の `/api/libraries/{id}/build/start` とはパスが異なる。

## 公開ファイルの配置方式

ライブラリ設定の「公開・配信 → 公開ファイル → 公開ファイルの配置方式」（`buildConfig.outputMode`）で選ぶ。

| 方式 | 文書の公開先（公開ルートからの相対パス例） |
| --- | --- |
| フォルダ階層を維持する（`STRUCTURE`、既定） | `部署/年度/案件/報告書.docx/` |
| フラットに配置する（`FLAT`） | `assets/0123456789abcdef/` |

フラット配置では、元のフォルダ階層やファイル名が長くても、文書の公開URLが長くなりにくい。文書ごとのフォルダ名には、ライブラリIDと正規化した元文書の相対パスから生成する16文字の識別子を使う。元のパスが短い場合も含め、常にURLが短くなることを保証するものではない。元文書の保存場所は変更しない。

フラット配置では「コンテンツ名をハッシュ化する」「名前の長さ（文字）」は適用されないため非表示にする。階層維持用の設定値は変更せず保存・再表示で保持し、階層維持に戻すと再表示する。名前の長さは従来どおりハッシュ化が有効なときだけ表示する。16文字の識別子を使う説明は配置方式の補足に残す。

方式を変更した後は全件再ビルドし、文書リンクを確認する。既存の文書リンクが変わる場合がある。元文書の移動・改名でも識別子が変わるため、フラット配置は固定URLを保証する機能ではない。

フラット配置の変換出力は `temp/{libraryId}/private-conversions/{buildId}/`、入力原本は `private-sources/{buildId}/` に置き、公開用の `temp/{libraryId}/{buildId}/` と分離する。HTML生成は変換出力を削除せず、公開前に成果物を非公開の `artifact-cache` へ保全してDB参照を切り替える。テンプレート再生成でも元文書の階層を公開ツリーへコピーせず、文書の公開先は `assets/{識別子}/` に統一する。SVG等の付属ファイルから `origin/` をまとめてコピーせず、原本は実効ダウンロード許可・取得方式に従って個別に配置する。

古い一時ビルドの整理では、そのビルドに対応する非公開入力・変換出力も削除する。DBが参照する永続キャッシュと公開済み版は一時領域の整理対象に含めない。公開失敗・キャンセル時も保全済みのDB参照を維持し、公開成功版の切替とは分けて扱う。

配置先の計算は [PublicationPaths](../../backend/src/main/java/jp/astack/backend/build/storage/PublicationPaths.java) を参照。

## 検索用の公開済み配置の確定（#6756）

全文検索の閲覧URL用に、公開処理開始時のライブラリ設定と文書一覧、公開計画の閲覧ページから配置情報を準備する。アップロード・削除・削除行整理・公開マニフェストの確定が成功した後、メインDBの `published_document` をライブラリ単位のトランザクションで更新する。公開前に候補を `published_document_pending`、未確定状態を `published_document_state` へ永続化する。途中失敗では旧配置を維持し、次回の公開で再試行する。配置DBの確定失敗後は、生成物のないDIFFもスキップせず、保存した候補と公開計画を照合して確定し直す。公開済み配置の切替と候補・未確定状態の削除は同一DBトランザクションで行う。DIRECT/STAGINGと差分公開のいずれでも同じ確定処理を通す。差分なしのスキップでは更新しない。

検索索引とは別の情報として保存し、再インデックスを公開配置の切替条件にしない。検索時の参照と導入時の再公開手順は [検索・公開閲覧](search-and-viewing.md) を参照。

## 原本取得の接続管理

公開前に原本をまとめてコピーする処理と、公開後の本文抽出は、一括処理の間に遅延接続した原本ストレージを再利用する。原本を取得しない処理では接続しない。接続はライブラリ・元文書接続ID・元文書ルートで分離し、処理終了・例外時に切断する。取得失敗後の接続は破棄し、次の取得で接続し直す。

事前変換の入力取得は、ライブラリ・ビルド世代・元文書設定ごとに接続を排他的に貸し出す。同じ接続を並列に使用せず、入力取得が成功した接続だけを次のファイルへ再利用する。接続定義の更新、取消、ビルド世代の終了、サービス終了時には古い接続を解放する。貸出中の接続は取得処理の終了時に閉じる。保持するアイドル接続の合計は変換ワーカー数以下とし、終了したビルドの接続は次回の変換ポーリングでも回収する。

オンデマンド変換であっても、原本のコピー配信を許可している場合は、その原本の準備を公開前に行う。本文抽出は公開後に実行する。原本の公開許可・版の整合性・更新確認方式は接続の再利用によって変更しない。

## 変換失敗と公開継続

個別変換の失敗で公開全体を中断せず、公開成功かつ変換失敗ありの場合は `WARNING`。この場合も公開処理は成功として扱い、ビルドモードが対象とする設定を反映済みにする。ジョブ状態は `WARNING` のまま維持し、失敗履歴も記録する。HTML生成や公開自体の失敗は `FAILED`、取消は `CANCELLED` とする。

`DocumentConfig.conversionFailurePolicy` は `KEEP_PREVIOUS`（既定）と `LATEST_ORIGINAL_ONLY`。旧版維持では最後の公開成功プレビューと対応原本を組にし、新しい原本を混ぜない。旧版がない場合や旧版不使用ではプレビューなしとする。原本公開は実効ダウンロード許可・取得方式に従う。失敗対象はログへ一覧化し、次回ビルドで再変換する。

## 変更のない差分更新

DIFFで文書の追加・更新・削除、フォルダの追加・削除がなく、HTML差分・公開設定変更・欠落出力の補完・未完了の削除もなければ公開処理をスキップする。ルート一覧は毎回再生成せず、変更による再生成判定と未公開フォルダの補完に従う。これにより共通資産・文書・一覧のコピーを行わず、公開ファイルの内容と更新日時を維持する。

変更なしもジョブは `SUCCESS` として実行日時・検知結果を履歴に残し、ログに「差分なし・公開処理をスキップ」と記録する。公開版の確定・公開完了イベント・`buildConfig.lastBuildAt` 更新は行わない。公開ページの `library.lastBuildTime` と新規・更新マークの基準は保存済みの公開日時を使い、差分確認だけの成功ジョブでは進めない。保存済み公開日時がない既存ライブラリに限り従来の成功履歴から補完する。

FULL/TEMPLATEはこの省略判定の対象外。DIFFでもテンプレート・ビューア・原本取得方法等の差分が生成・整理対象を作る場合、失敗した削除の再試行、未公開フォルダの補完は実行する。原本取得方法がSOURCE/DISABLEDのままなら、公開先の原本削除要求を毎回繰り返さない。新しい成果物への原本混入防止は継続する。

## 削除文書の公開とDB整理

原本削除の検知時に検索・要約・使用中のベクトル索引と変換ジョブを削除し、ライブラリDBの `build_file` を論理削除する。削除情報は親一覧・ツリーの更新と公開先の整理に使用する。

通常公開・差分公開とも、公開開始時に削除済みファイルのIDを確定する。DIRECT公開では文書フォルダと削除フォルダを除去し、STAGING公開では公開ツリーの置換で反映する。フラット配置では元フォルダの削除・非公開化による整理を一覧の `index.html` に限定し、共有 `assets/` と他文書の公開先を再帰削除しない。文書の公開先は文書ごとの削除処理で整理する。同じパスに有効な文書がある場合、その公開文書は削除しない。

公開先の整理・後処理が成功した後、今回処理したIDかつ引き続き削除済みの行だけを単一SQLでDBから一括削除する。公開失敗・DB削除失敗時は削除情報を保持し、次回公開で再試行する。後から削除された別の行、有効な文書、文書個別設定、ジョブの実行履歴は一括削除の対象にしない。削除履歴はビルドログに残す。

## コンバーター未対応ファイルの公開

ライブラリの公開設定に次の2項目を持つ。

| 項目 | 保存先 | 動作 |
| --- | --- | --- |
| コンバーターが対応していないファイルの扱い | `documentConfig.publishUnsupportedFiles` | `true` は公開、`false` は非公開。未設定の既存ライブラリも非公開 |
| 例外として公開する拡張子 | `documentConfig.unsupportedFilePublicExtensions` | 非公開を選択した場合のみ表示。カンマ区切りで指定した未対応形式を例外公開する |

拡張子に関する公開設定は、この2項目に集約する。旧「公開ファイル拡張子」と「指定以外の拡張子を非公開にする」は廃止し、旧JSONの `extensionPublishBrava` と `unPublishOtherExtensions` は定義・互換処理からも削除する。旧値の引き継ぎは行わず、対応形式は通常の公開対象とする。一部の形式を取り込み対象から外す場合は「除外設定」を使用する。

例：非公開＋`zip`では、未対応のHTMLは非公開、ZIPは一覧に掲載して原本をダウンロードできる。先頭のドット・大文字小文字は区別しない。空欄は例外なし。公開へ切り替えている間も例外の入力値は保持する。

選択中の変換プロファイルのエンジンが入力拡張子に対応するかで判定する。エンジンの対応拡張子が未指定の場合は従来どおり全形式対応として扱う。出力形式と同じ原本は既存の変換省略で閲覧できるため対象外とする。対応形式の変換失敗は本設定と区別し、変換失敗時の公開方針に従う。

公開例外は、取り込み除外、文書・親フォルダの公開除外、公開期間、認証・ACLを解除しない。未対応形式の公開はプレビューの提供を意味せず、ダウンロードの許可・取得方式は従来の実効設定に従う。

公開した未対応ファイルには、プレビュー非対応の案内と利用可能なダウンロードリンクを表示する。コピー方式では変換処理を経由せず原本を取得し、原本の変更時にも差分で更新する。原本は添付ファイルとして配信する。非公開ファイルは一覧・検索から除外し、原本・プレビュー・短縮リンクへの直接アクセスも禁止する。

本体の配信判定は保存後の最新設定を使用する。静的な公開先の一覧更新・原本の削除は次回ビルドで反映する。非公開化による削除は公開成功まで再試行する。設定は既存のライブラリ設定JSONに保存し、DBの列追加は不要。編集権限は既存の公開設定と同じく管理者に限定する。

## 原本ダウンロード

アクセスログの共通資産・HTMLへの組み込み、再公開条件は [アクセスログ仕様](access-log.md) を参照。ログ有効化・APIパス変更を差分生成の判定に含める。

実効 `enableDownload` と既存名 `copySourceDocumentToLiblary`（綴りを含め保存形式を維持）で取得方式を決める。文書個別設定を優先し、未設定ならライブラリを継承する。

| 設定 | 動作 |
| --- | --- |
| 許可＋コピー有効 | 公開先 `origin/` にある対応原本を配信 |
| 許可＋コピー無効 | `GET /pub/{libraryKey}/_api/files/{fileId}/download` で取得時点の元文書を取得 |
| 不許可 | 公開原本を残さず、API要求も拒否 |

API取得の原本が最後の変換版と同一とは限らない。外部公開では「公開・配信 → 外部Webサーバ → APIパス」（`pathConfig.apiPath`）を優先し、空欄ならシステム設定 `publication.api-path` を継承する。内部公開ではAPI設定を参照せず、公開サイト配下のAPIを使用する。ショートリンクと同じ接続先を使い、実効APIパス配下に `/pub/{libraryName}/_api/files/{fileId}/download` を付与する。APIパスはHTTP/HTTPSのベースURLまたは `/` から始まる同一サイト内のパスで、認証情報・クエリ・フラグメントを含めない。コピー配信の原本URLは引き続き公開先の `origin/` を使う。

直接接続ではS3等の静的ページからもAstackの原本取得APIへ通常のダウンロードリンクで遷移する。JavaScriptで原本をfetchしないため、この取得のためにCORSの許可範囲を広げない。ダウンロード許可・公開条件・通常の認証・祖先フォルダと文書ACLの検査を維持する。Windows認証を適用するパスの判定ではサーバーのコンテキストパスを取り除く。

リバプロ経由ではAPIパスに公開側のベースURLを設定し、発行API・ダウンロードAPIと `/s/...` の経路、Windows認証ヘッダー・チャレンジをAstackへ転送する。APIと短縮URLの認証結果・転送結果を共有キャッシュしない。接続方式の選択・疎通確認・自動切替は行わず、通信・認証環境は利用者側で管理する。

ライブラリ・システムの両APIパスが未設定の既存構成では、ダウンロードは従来のサイトURL配下の `_api/files/...` を維持する。この未設定構成で外部公開する場合は引き続きリバプロが必要。共通値は不足時のみ空欄で登録し、既存の経路を自動変更しない。APIパス変更は差分判定に含め、再ビルドで文書・一覧のリンクを更新する。NTテンプレートの原本取得はコピー無効時も許可されたAPIリンクを表示し、ExplorerViewの文書画面にも原本取得ボタンを設ける。

取得方式の変更は原本が未変更でもDIFFでHTMLを再生成し、不要になった公開原本を削除する。公開成功時の状態を `download-publication.properties` に記録する。非公開の変換・履歴用原本や元ストレージは公開原本の整理対象ではない。

## 実行元、採番、画面

ビルド・AIに `MANUAL`、`SCHEDULE`、`BUILD_JOB`、`AI_JOB`、`UNKNOWN` と実行者・起点ジョブ・スケジュールの情報を保存する。手動の再実行は新しい操作ユーザーを記録する。過去行に記録がなければ「記録なし」。ビルド・AI・変換のIDは種類ごとのIDENTITYで、H2のNO CACHEにより先取りによる再起動時の欠番を抑える。既存IDと適用時点の次回採番位置は変更しない。過去の欠番や削除・ロールバックによる欠番を埋める保証はない。

画面は `/builds` のジョブ管理。ビルド・AI処理・ファイル変換・スケジュールをタブ表示し（ファイル変換とスケジュールは管理者のみ）、ID指定の詳細リンク、実行ユーザー・実行元、再実行・ログ操作を提供する。ビルド一覧は実行モードを表示し、AIは実行条件を詳細に表示する。ビルド・AI処理の一覧には実行時間を表示し、実行中（AIのキャンセル中を含む）は毎秒更新する。未開始は `-`、完了後は開始から終了までの固定値を表示する。AI処理の一覧には消費トークン数（合計）も桁区切りで表示し、未記録は `-`、記録された0は `0` とする。変換タスクの `buildJobId` は親ビルドから対象を解決する。既存の親IDなしタスクは推測で紐付けない。ファイル変換一覧は `/builds?tab=conversions` で開き、旧 `tab=jobs&view=conversions` のリンクも同じタブで表示する。失敗・ファイルごとの最新タスクの絞り込みは維持する。

## 前回ビルドのバックアップ設定（未提供）

Astack4では、利用者向けの前回公開結果の保持・復元機能は未提供とする（[#6724](https://developer.astack.jp/redmine/issues/6724)）。保持世代・容量上限・復元操作と各公開先の対応が未定義のため、「最後のビルド結果をバックアップする」はライブラリ画面に表示しない。公開途中のロールバック用一時バックアップは、成功時に削除される従来の内部処理であり、利用者向け保持を保証しない。

`documentConfig.enableBackUpLastBuild` は既存JSON・API・インポートとの保存互換性のため読み書きを維持する。既存のtrue/falseを編集・再保存で変更せず、値にかかわらず保持・復元処理を実行しない。新規値はfalse。既存データの一括移行や削除は行わない。
## ファイルレジストリ設定（未提供）

「ファイルレジストリを有効にする」の利用者向け切替はAstack4では未提供とする（[#6727](https://developer.astack.jp/redmine/issues/6727)）。登録情報の範囲・更新削除・差分判定との関係が定義されておらず、実行系への参照もないため画面に表示しない。クロール・文書登録・差分検出は既存のパイプラインに従い、このフラグで変更しない。

`buildConfig.fileRegistry` はAPI・既存JSON・インポートとの保存互換性のため読み書きを維持する。既存true/falseを編集・複製・再保存で保持し、新規値はfalseとする。値にかかわらず追加の登録機能や処理分岐を提供しない。データの一括移行・削除は行わない。

前回ビルド結果のバックアップ（[#6724](https://developer.astack.jp/redmine/issues/6724)）、ライブラリの差分・次回全件・毎回全件設定（[#6725](https://developer.astack.jp/redmine/issues/6725)）、ファイルレジストリ（[#6727](https://developer.astack.jp/redmine/issues/6727)）の項目除去は暫定対応とする。これらの機能は今後追加する予定であり、機能の実装・検証が完了するまで各チケットは未完了として維持する。画面項目の非表示や現行ジョブモードへの一本化だけで解決・クローズしない。既存保存値は互換性のため保持し、再提供時の仕様・移行方針は各機能の実装時に定義する。


## 配信方式と公開後変換（#6794）

`buildConfig.deliveryMode` は `CONNECTED`（Astackと連携して配信、既定）と `STANDALONE`（公開ファイルだけで配信）。STANDALONEではPRECONVERTを必須とし、アクセスログ・ショートリンク・Astackによる閲覧権限確認を無効にする。原本ダウンロードを許可する場合は公開先へコピーする。文書個別設定によってAPI取得へ戻さない。公開先Webサーバーの認証・アクセス権は運用側で設定する。

公開ページのAPI検索は表示せず、検索APIの対象からも除く。一方、ビルド環境の本文抽出・索引作成・AI処理の設定は維持でき、生成した要約・タグは静的HTMLへ反映できる。通常のURLコピーとブラウザ内のQR生成は利用可能。保存・設定インポート・ビルド開始で矛盾する設定を拒否する。フォームでは配信方式の変更内容を表示し、保存・全件再ビルドで反映する。

事前変換の公開物はビューア・マニフェスト・変換済みファイル・必要なライブラリやフォントを含み、閲覧用変換APIを呼ばない。Astackへの通信を遮断しても独立したHTTP(S)配信で閲覧できる。原本の変更は次回ビルドで反映する。

BACKGROUND/ON_DEMANDは閲覧時にAstackへのAPI接続が必要。内部WebサーバではAPI設定は不要で、ライブラリのAPIパス・共通の公開API URLを参照せず、閲覧中の公開サイト配下のAPIを使う。初期対応は公開ページと同一オリジンのAPI経路とし、リモート公開は公開側の中継パスを設定する。別オリジンへビューアの取得制限を緩和しない。バックグラウンド変換完了後の独立配信用確定操作は今回の初期提供範囲外。

HTML公開ジョブと公開後の文書変換は別の状態として扱う。公開後の変換失敗で公開成功を巻き戻さない。旧版維持の設定は現在の文書アクセス権を満たす場合だけ適用し、旧版の表示であることを起動画面へ通知する。

### ファイル変換一覧の統合

「ファイル変換一覧」はビルド時の変換と公開後の変換を統合し、変換方式（事前／バックグラウンド／オンデマンド）を表示・絞り込みする。`GET /api/build/convert-jobs` は `conversionTiming` を受け付け、両キューの統合後に状態・エンジン・ライブラリ・文書検索・ソート・ページングを適用する。アクセス権のあるプロジェクトのライブラリだけを件数・一覧に含める。

オンデマンドではビルド時に未閲覧文書のタスクを作成せず、閲覧要求時に必要な文書だけを登録する。未要求の状態は起動APIで `WAITING` と返すが、タスク一覧には行を作らない。`QUEUED` は「待機中」、`RUNNING` は「処理中」、`READY` は一覧では `SUCCESS`（完了）、`FAILED` は「失敗」とする。方式と処理状態は別項目とし、原本や暗号化された接続設定を一覧へ返さない。`taskKey` はキュー間のID衝突を防ぐ。公開後変換は文書ごとの現在の版・最新試行を表示し、全試行の履歴一覧ではない。

ビルド詳細内の一覧は従来どおりそのビルドのタスクだけを対象とし、公開後の変換を推測で親ビルドへ関連付けない。全体一覧は新規要求も定期取得する。公開後タスクの日時は導入後から記録し、記録のない既存日時は `-` とする。変換の実行枠は事前変換と共有する。閲覧要求は優先度100、通常のバックグラウンド変換は0とし、待機中の閲覧要求を先に実行する。事前変換と通常のバックグラウンド変換は同じ優先度で、共通スケジューラーがライブラリごとの「通常変換の優先確保数」を目標に配分する。目標未達を充足率・最後の割当順に優先し、余剰枠は両キューの受付順に使う。実行中の変換は中断せず、全体・エンジン別の同時実行上限を維持する。固定のビルド予約枠は設けない。詳細は [変換の割り当て](conversion.md#ライブラリ間の割り当て) を参照。

公開後のオンデマンド変換は、変換済み成果物が存在し、原本・変換設定が同じならFULL公開後も再利用する。原本更新・設定変更・成果物欠損は次回の閲覧要求で再予約する。実行中の旧設定タスクが再公開で無効になった場合は完了成果物を復活させず、表示中の起動ページが新しい公開版を再要求する。既存の未要求 `WAITING` 行は起動時に除去し、要求済み・完了済みの行を保持する。


## サムネイルの公開（#6838）

サムネイルは公開成功の必須条件としない。事前変換では画像生成の試行分だけ処理時間が加わるが、未生成・生成失敗を理由に公開を止めない。画像も文書の付随成果物として外部公開先へ転送する。

バックグラウンド／オンデマンド変換と、オンデマンドの「サムネイルを順次生成する」では、公開後の文書成果物と同じ認可付きAPI経路から画像を配信する。`GET /pub/{libraryKey}/_api/files/{fileId}/preview/thumbnail` は画像の有無を確認するだけで変換を予約しない。文書の公開状態・フォルダ階層・転送セキュリティを確認し、現行版のPNGだけを `image/png`・`nosniff`・`no-store` で返す。未生成時の404もキャッシュさせない。

外部公開の後の2方式は既存の同一オリジンAPI中継を使用し、サムネイル完成のためにHTML全体を再公開しない。独立配信は従来どおり事前変換に限定する。
