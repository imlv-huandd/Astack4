# 運用・監視・ログ採取

確認基準は [索引](../README.md) を参照。

ライセンス状態の確認、登録・更新、インストールID、監査・中断復旧、正式鍵の配備前提は [ライセンス管理・利用制限](licensing.md) を参照する。未登録・期限切れ等の間も認証・復旧と既存の公開閲覧を維持する。

## ライセンスの再発行・復元

管理者は `/settings/license` の現在インストールID、OS認識ホスト名、認証対象IPv4を確認する。「発行依頼情報をコピー」でIDとホスト名を取得し、発行担当者へ伝える。IPアドレスはコピー内容に含めず、自動送信もしない。

ホスト名・DHCPを含む対象IPv4・NIC構成を変える前に、ライセンスの再発行が必要になることを確認する。バックアップはライセンス保存先一式とメインDBを同じ世代で取得し、復元は停止中に行う。同じ初回日時・ホスト名・対象IPv4の集合ならIDを保持できるが、移設や異なる環境への復元では管理画面の新IDで再発行する。記録削除によるID再生成や体験期限の延長を復旧手順にしない。

旧UUIDv4で認証中と表示された場合も、再発行先は表示中の新UUIDv8。旧ファイルの再アップロードは新方式の登録条件を満たさない。ID未取得時はホスト名・NIC/IPv4・初回日時の保存データを調べ、対応するバックアップを復元する。詳細と旧正式ライセンスの経過措置は [ライセンス仕様](licensing.md#端末に紐付くインストールid) を参照する。

## ダッシュボードとジョブ管理

管理者向け画面の上段は「ファイル・プロジェクト概要」「ビルド状況」「AI処理状況」の順に3列で表示する。狭い画面では同じ順序で縦に並べる。概要は管理者のみに表示し、それ以外の利用者はビルド・AI処理の2列構成とする。

管理者向けダッシュボードは拡張子別統計、ライブラリ別日次統計とビルド・AIの処理状況を表示する。状態別の件数と表示する先頭件数を分け、取得失敗を0件や正常な空一覧に置換しない。ビルドにはWARNING、AIにはCANCEL_REQUESTEDがある。種類の異なる同一IDは別ジョブ。

上部の「ビルド状況」「AI処理状況」は同じUIで、成功率・色別の割合バー・結果内訳を表示する。ビルドの内訳は成功・警告・失敗・キャンセル、AI処理は成功・失敗・キャンセル。実行中・待機中の件数をカード下部へ表示し、AI処理はキャンセル中も表示する。統計欄には重複するビルド結果を置かない。全件数は当日を含む直近30日（当日から29日前〜当日）に投入されたジョブの現在の状態で集計し、期間外の履歴は含めない。ビルドのWARNINGはSUCCESSと区別する。各件数はリンクとし、`/builds` の `tab`・`status`・`dateFrom`・`dateTo` に同じ条件を渡す。

従来の最近失敗したジョブ・実行中／待機中のジョブ・最近の完了ジョブの3一覧は表示しない。代わりに管理者向けに「変換に失敗しているファイル」を表示する。管理者限定API `GET /api/build/failed-conversion-files?page=0&size=10` を使用する。各ライブラリID＋ファイルIDの最新タスク（最大ID）を選び、その状態がFAILEDのものを保管先を含む元文書パスでライブラリ横断集約する。最新が成功・待機・実行中などの場合、過去の失敗は表示しない。失敗日時降順・同日時はID降順で取得し、各グループは最も新しい失敗の順に並べる。全件を集約してから総件数・ページングを計算し、期間制限なしで10ファイルずつ表示する（APIのsizeは1〜100、pageは0以上）。

ローカルは接続ルート＋元文書パス＋ファイル相対パスを絶対パスへ正規化し、同じ場所を指す異なる接続や直接指定もまとめる。CIFSはホスト・ポート・共有名・元文書パス・相対パス、S3はエンドポイント・バケット・元文書パス・相対パスで識別する。FTP/FTPS/SFTPはアカウントごとのルートの差を考慮し、接続ID＋元文書パス＋相対パスで保守的に識別する。パスは実際のプロバイダーと同じ規則で正規化する。ネットワークアクセスや実ファイル検査は行わないため、シンボリックリンクやホスト別名の同一性は判定しない。元文書情報・接続設定が不明の場合はライブラリID＋ファイルIDを保持し、誤って他のファイルとまとめない。認証情報は応答に含めない。

ファイル名・保管先を含むパス・失敗中のライブラリ名一覧・最新のコンバーター／理由／日時・重複除外後の総ファイル数を表示する。複数ライブラリの場合は「ライブラリごとの内訳」を展開して各コンバーター・失敗理由・日時を確認できる。15秒ごと・画面復帰時・更新ボタンで再取得し、失敗や未取得を正常な0件と区別する。再取得失敗時は前回の結果と警告を表示する。一般ユーザーから同APIへアクセスしない。従来の `convert-jobs` APIと `latestPerFile` の省略時falseの挙動は維持し、履歴一覧を変更しない。

変換失敗一覧から `/builds?tab=jobs&view=conversions&status=FAILED&latestPerFile=true` へ遷移し、失敗で絞った変換タスク一覧を表示する。ビルド・AIの件数の30日条件はそのまま維持する。統計の各カード・ファイル数推移の期間選択は残し、「統計」という可視見出しは置かない。

ジョブ管理のビルド・AI処理一覧には投入日の開始日・終了日を設け、ステータスと組み合わせて絞り込める。開始日のみ・終了日のみの指定と期間解除にも対応する。ダッシュボードからの遷移では日付とステータスを入力欄へ反映し、条件変更時は先頭ページに戻る。開始日が終了日より後ならエラーを表示する。

一覧API `GET /api/builds`・`GET /api/ai-jobs` は省略可能な `dateFrom`・`dateTo`（`YYYY-MM-DD`）を受け取る。保存された投入日時 `createdAt` を開始日0時以上・終了日の翌日0時未満で検索する。日付なしは従来の全期間。DB検索時に権限・状態・日付を適用してからページング・総件数を計算する。不正な日付・逆転した期間は400を返す。

処理状況は表示中15秒ごと、詳細は活動中3秒ごとに更新する。詳細・ログ・再実行はジョブ管理と共用する。統計の更新は処理状況と独立させる。ライブラリ別ファイル数推移の期間は、グラフ内右上の7日・30日・90日ボタンで選択する（初期値30日）。選択中の期間を強調表示し、対応する期間の統計を再取得する。日次総サイズは変換後容量ではなくスキャン済み原本のサイズであり、集計時点も表示する。概要には「総ファイルサイズ（変換後）」も表示する。削除されていない変換成功ファイルが現在参照する主成果物と付属ファイルを集計し、原本のoriginディレクトリ、過去版、同じ成果物パスの重複を除外する。成果物が欠損した場合や導入前の履歴はnull（未集計）として扱い、0に置換しない。既存の日次集計で更新し、導入時は当日の未集計分を起動後に一度補完する。

上部の結果サマリーは状態別APIの総件数を使用し、100件で打ち切らず直近30日間の全件を集計する。成功率は成功÷（成功＋失敗）×100を四捨五入し、WARNINGとCANCELLEDを除外する。成功＋失敗が0件なら「集計対象なし」。割合バーの母数は終了済みの結果内訳すべてで、警告とキャンセルも含める。取得失敗や未取得がある場合は成功率・割合バー・対象件数を確定せず、取得できた状態の個別件数は表示する。最終成功日時は同期間のSUCCESSの終了日時から選ぶ。ビルド・AIとも15秒ごとの更新と同じ期間のリンクを使い、一般ユーザーにも既存の閲覧権限の範囲で表示する。

統計欄のビルド所要時間トレンドは同じ直近30日間を対象とし、投入日時降順の最大100ジョブから集計する。

## システム情報と診断

システム管理の「バージョン」とサイドメニューフッターは、同じ `displayVersion` を使用し、`製品版（ビルド識別情報）` として表示する。製品版はライセンス判定と共通の `ProductBuildVersion.VERSION`、ビルド情報はビルド時に生成した `git.properties` の値を使用する。

| ビルド状態 | 表示例 |
| --- | --- |
| HEADに製品版と一致するリリースタグあり | `4.0.0（release-v4.0.0-abcdef0）` |
| タグなし、または一致するリリースタグなし | `4.0.0（main-abcdef0）` などブランチとコミットID |
| detached HEADなどブランチ情報なし | `4.0.0（abcdef0）` |
| Git情報・コミットIDを取得できない | `4.0.0` |

`git.tags` に複数タグがある場合も、製品版と完全一致する `release-v{製品版}` のみをリリース表示へ採用する。別名タグ・異なる版のタグから製品版を変更・推測しない。フッターでは長い識別子を折り返して表示する。ライセンスの対象範囲は製品版だけと照合し、タグ・ブランチ・コミットIDを判定へ使わない。

推奨するリリース運用は、(1)製品版・承認済み公開鍵をPRで確定、(2)テスト成功後にマージ、(3)対象コミットへ注釈付き `release-vX.Y.Z` を作成、(4)そのタグからビルド、(5)同一の成果物を検証・配布・保管する手順とする。公開済みタグの付け替えや同一版の差し替えは避け、修正は新しいパッチ版で公開する。将来のリリース用CIではタグとコード定数の一致・作業ツリーのクリーン状態を検査する。本変更ではリリースタグの作成・リリース用CIの追加は行わない。

公開設定取得は `/api/system/config`。詳細診断は管理者限定の `/api/system/diagnostics/metrics`、`/database`、`/opensearch` に分離し、Cache-Controlをno-storeにする。

CPU・メモリ・稼働時間は画面表示中5秒、DB/OpenSearchは30秒ごとに取得する。非表示時は停止、復帰時に再取得し、通信失敗時は前回値と警告を示す。不明値はnull等で表し、固定の「正常」や0へ置換しない。依存先診断は専用ワーカーとAPIの4秒待機上限で障害を分離し、URL・資格情報や例外本文を応答へ含めない。

## 変換ワーカー数の詳細設定

システム設定の詳細設定一覧に「全体の変換ワーカー数」（キー `build.converter.concurrency`、カテゴリ `SYSTEM`）を初回起動時に登録する。範囲は1〜64の整数。既存設定を上書きせず、未登録時のみ同名の起動設定（既定4）をDBへ引き継ぐ。編集モーダルは整数入力と範囲・反映時期を表示し、新規作成・編集・値更新APIすべてで値を検証する。

保存後は次回の処理確認（通常5秒間隔）で反映し、再起動は不要。全体上限とエンジンごとの上限の両方を適用する。縮小時に実行中の変換を中断せず、使用枠が新しい上限を下回るまで追加起動を待つ。無効・削除時は起動設定へ戻り、削除された設定は次回起動時に再登録する。DB内の既存不正値には警告を残して起動設定へ戻す。DB取得失敗時は古い値で新規処理を開始せず、実行中処理を継続して次の取得を待つ。

## ログ

生成コンテンツの操作履歴は [公開コンテンツのアクセスログ](access-log.md) を参照。管理画面の「アクセス履歴」はADMIN限定。サポート採取やアプリケーションの実行ログとは分離し、DBの未送信キューから専用OpenSearchインデックスへ非同期転送する。登録済み本文はDBから削除し、再送防止用の短期レシートを保持する。移行済み履歴のバックアップにはOpenSearchスナップショットも必要。初期実装はAPI直接送信で、Webサーバ/CDNのログ取り込みは含まない。保存総件数にアプリ固有の固定上限はなく、CSVは1回10000件まで。保存期間は既定0（無期限）で、管理画面から全ライブラリ共通の日数を設定する。削除はOpenSearchで毎時の分割処理となるため、容量・バックアップと期限切れ履歴の残件数を運用で確認する。未送信本文は削除しない。連携失敗時はサーバログとキュー滞留を調べる。旧DB検索版への復旧は [連携設計](access-log-opensearch.md) の移行・復旧手順に従い、旧writerを混在させない。

実際の出力先・ローテーションは `logback-spring.xml` を参照する。アプリ、監査、認証・権限、ビルド、AIのログを区別する。ビルド・AI・検索インデックスはジョブのログ表示・ダウンロードを提供する。検索インデックスのログレベルはビルドと同じ1〜5の基準で、検索専用設定が未指定ならビルド設定を継承する。AIのライブラリ別ログレベルは1=ERROR、2=WARN、3=INFO（既定）、4=DEBUG、5=TRACE。秘密情報を出力しない。

旧ログ戦略にある「コンソールのみ」という現状分析や将来ロードマップは当時の記録。現在のファイル出力設定やサポート採取と混同しない。

## サポート採取

管理者専用 `/support` と `/api/support` で条件選択、事前確認、非同期採取、状態取得、取消、ZIPダウンロード、保持履歴の削除を提供する。初期条件は直近24時間・アプリログ・環境情報。期間とログ種別、ライブラリ・ビルドID・AI IDで絞り込める。

ZIPは `summary.txt`、`manifest.json`、任意の `environment.json` と `logs/`。認証情報を設定収録から除き、ログ中の秘密値も除去する。外部ストレージの接続試験を採取時に自動実行しない。ジョブ集計は採取時点の集計。

| 制限 | 実装の値 |
| --- | --- |
| 展開後ログ読み取り合計 | 既定1024MiB、`support.bundle.max-read-mib` |
| ZIP圧縮前収録合計 | 既定1024MiB、`support.bundle.max-archive-mib` |
| 上記2設定の範囲 | 各1〜10240MiB、次回採取から反映 |
| 期間・件数 | 最大31日・1000ファイル |
| 環境情報等の単一ファイル | 10MiB |
| 同時作成・保持 | 1件・60分、完成ZIP最大5件 |

上限は開始時に固定し、上限種別・到達量・対象ファイルを失敗状態に記録する。読み取り上限は期間外の行を読み飛ばす処理も含む。途中ZIPは配信せず、失敗・取消・期限後に削除する。

## DB、配布物、検証

メインDBはプロジェクト・接続・ビルド/AIジョブ等、ライブラリDBは走査・変換成果物等を管理する。通常・dev設定はH2ファイルとddl-auto=update、prod設定は外部DB接続とddl-auto=validate、testはcreate-drop。組み込みメインDBはDB_CLOSE_DELAY=0とプールcloseで終了する。外部TCP DBへSHUTDOWNを送る仕様ではない。

`docs/dist/` は過去配布物。新しいWindows配布物は `build/build-windows-installer.sh` で同ディレクトリ配下へ生成する。既定のJAR作成は `build/build-jar.sh`。配布物の生成と本番適用は別操作。

今回の整理はドキュメント、参照コメント、関連ビルドパスが対象。過去記録にある実機・AWS・ブラウザ検証を今回の実施結果として扱わない。今回の検証記録は [整理記録](../reorganization.md) に記載する。

## ログストリームの認証と漏洩対策（#6683）

ビルド `/api/build/logs/{libraryId}/{logId}/stream` とAI `/api/ai-jobs/{jobId}/log/stream` は、`fetch` の `Authorization: Bearer` ヘッダーで認証する。通常JWTをURLへ含めない。SSEとWebSocketを含めクエリ `token` は認証として受け付けない。JWTの検証・現在の資格情報との照合・プロジェクト/ライブラリの閲覧認可は既存処理を継続する。旧クライアントは更新が必要。

ストリームはUTF-8/SSEの分割チャンク・複数data行を処理し、`done` で停止する。通信切断/5xx時は3秒後に再接続し、サーバーの全文再送に合わせて表示をリセットする。401（期限切れを含む）と他の4xxは再試行せず画面に理由を表示する。画面を閉じるか対象を変更すると要求と再試行タイマーを中止する。接続後にJWT期限が到来した場合は従来同様、その接続を継続し、再接続時に再検証する。

進捗通知も通常JWTのURL送信を廃止し、ビルド・AI・変換一覧は既存ヘッダー認証APIを使用する。活動中は3秒、活動がない場合も新規ジョブ検知のため15秒で取得する。非表示タブでは定期取得を止め、重複する定期要求を抑制し、画面離脱時にタイマーを解除する。通信障害時は次の定期取得で回復を試みる。WebSocketサーバー自体は残すが、クエリJWTは無効。

Logbackのコンソール/アプリ/監査/認証ログは、本文・例外・MDCを出力直前に `SupportLogSanitizer` でマスクする。ビルドへのLogbackミラーにも同じ処理を適用する。サポートZIPは従来どおり採取時にもマスクする。既定/devのSpring Security DEBUGでも拒否された旧URLのtoken値を出力しない。prodのWARN設定は追加防御であり、マスクの代替ではない。

リポジトリにはリバースプロキシのアクセスログ設定を同梱していない。Tomcatアクセスログは既定で無効。外部プロキシ/ロードバランサーの実設定は導入先で確認する。アクセスログへクエリやAuthorization/Cookieを記録せず、nginxなら `$request_uri`/`$request` の代わりに `$uri` とメソッド・ステータスを記録する。アプリからプロキシが先に記録する旧URLをマスクすることはできない。

既存漏洩の調査・対処は次の順で実施する。生JWTをチケットや調査資料へ転記しない。

1. 旧クライアントを停止し更新する。対象期間・環境（既定/dev DEBUG、prod、外部プロキシ）と閲覧可能者を特定する。
2. アプリ/認証/アクセスログ、ローテーション、バックアップ、共有済みZIPをアクセス制限下で調査する。共有を止め、保持方針に従い隔離・削除またはマスク版へ置換する。監査証跡の保存要件も確認する。
3. 漏洩の可能性があるユーザーのパスワードを変更する。現行の資格情報照合によりそのユーザーの既発行JWTは拒否される。ログアウトだけでは失効しない。全ユーザーに影響する署名鍵の変更は、再ログインと全ノードへの同時反映を計画して承認後に行う。既定の24時間だけで影響なしと判断しない。
4. 識別可能なダミートークンで、ブラウザー要求URL・アプリログ・外部アクセスログ・サポートZIPを確認する。Authorizationヘッダーは共有するHAR等からも除去する。実環境の旧ログ処理と資格情報失効は運用者が実施記録を残す。

リリース時はフロントエンドとバックエンドを同時に更新する。リポジトリ内の追跡済み静的資産をそのまま包装せず、`frontend` で `npm ci && npm run build` を実行してからバックエンドを包装する。`mvn package` だけではフロントエンドを再生成しない。旧UIと新APIの組み合わせでは旧クエリ認証が拒否される。

## 公開APIの接続先設定

有効な共通公開API URLがHTTP/HTTPSの絶対URLの場合、そのオリジン（スキーム・ホスト・ポート）を管理画面の静的リソースと通常APIのCORS許可元へ自動追加する。ALB等のHTTPS終端後にバックエンドへHTTP転送されても、公開URLを別途CORS設定ファイルへ追記する必要はない。末尾の `/` やパスは許可元に含めず、ホストとスキームを小文字化し既定ポートを省略する。既存の `cors.allowed-origins` は保持し、設定の保存・変更・無効化・削除を次の要求から反映する（再起動不要）。空欄・相対パス・無効な旧値は追加しない。ライブラリ個別のAPIパスは管理画面の許可元には追加しない。ショートリンク・アクセスログ・sandboxプレビューの専用CORSと既存の認証・権限制御は維持する。URLから接続先を自動検出したり、転送ヘッダーの信頼範囲を変更したりはしない。


外部Webサーバへ公開する場合は、システム設定の「システム情報 → 稼働状態 → 公開API URL」を公開ページからの共通接続先として使用する。内部WebサーバではAPI設定は不要で、ライブラリのAPIパスと共通設定を参照せず、閲覧中の公開サイト配下のAPIを使用する。API接続先は外部公開時だけ表示する。「公開・配信」で内部/外部の配信先を選び、リバースプロキシ連携は配信先と独立して選択する。内部公開も前段のリバースプロキシ経由で配信できる。文書閲覧権限と通常の認証は継続する。ポート番号の下に表示し、鉛筆アイコンから編集する。保存先は既存の `publication.api-path`（カテゴリ `SYSTEM`）で、詳細設定一覧には表示しない。一覧APIの `excludeKey` にこのキーを指定し、検索・カテゴリ絞り込み・ページ分割・件数集計の前に除外する。キーを指定しない従来の一覧API、設定の取得・更新API、エクスポートは維持する。未設定・無効・取得失敗を区別して表示し、取得失敗時は再取得するまで編集できない。設定が削除済みの場合は編集・保存時に再作成する。ライブラリの「公開・配信 → 外部Webサーバ → APIパス」（`pathConfig.apiPath`）を優先し、空欄なら有効な共通設定を継承する。初期値は空欄で既存値を上書きしない。Astackの待ち受けポートとは独立して管理し、URLへのポート自動連結は行わない。HTTPの80番・HTTPSの443番は省略でき、独自ポートはURLに明示する。変更後は対象ライブラリを再ビルドする（Astackの再起動は不要）。HTTP/HTTPSベースURL、または `/` から始まる同一サイト内のパスを受け付ける。クエリ・フラグメント・認証情報を含む値は設定の作成・更新・値更新APIで拒否する。管理者だけが共通値・ライブラリのAPIパスを変更できる。一般ユーザーによる通常更新では元のパス設定を維持し、新規作成時の指定は使用しない。

ショートリンク発行とコピー無効時の原本ダウンロードで共通利用し、接続方式の選択や自動判定は行わない。公開サーバー／CloudFront等で中継する場合は、その公開URLとAPI・短縮URLの中継経路を設定する。直接接続では閲覧ブラウザからAstackへ接続する。疎通や到達性を保証しない。認証情報の転送、必要なCORS、HTTPSやブラウザの認証制約は環境に合わせて運用する。

共通値はビルド開始時点で固定し、APIパス変更後は対象ライブラリを再ビルドする。共通設定が無効・空欄の場合もライブラリ指定は優先する。両方未設定では従来のダウンロード経路を維持する。URL変更は配布済み短縮コードを失効させないが、旧接続先の到達性を継続するかは運用で管理する。

旧 `buildConfig.shortLinkServerUrl` は設定の読み込み・保存時に `pathConfig.apiPath` へ引き継ぎ、以後はAPIパスだけを保存・表示する。既にAPIパスが存在する場合（明示的な空欄を含む）は新設定を優先し、旧値を復活させない。旧URLの引継ぎ後は原本API取得も同じ接続先を使用する。

## 公開初期設定と管理者向け診断（#6729）

匿名許可の `GET /api/system/config` は画面初期化に必要な `displayVersion` と `defaultTemplateId` のみ返す専用DTOとし、JVM/OS、起動時刻、ポート、CPU・メモリ、テンプレート保存パス・制限値を返さない。新たな診断項目を公開DTOへ追加しない。

従来の詳細情報は `GET /api/system/diagnostics/config` へ分離し、ADMINのみ許可する。匿名は401、一般ユーザーは403。システム設定画面は認証後にこのAPIを取得し、グローバルな公開設定Contextに内部診断を保持しない。両APIは `Cache-Control: no-store` とする。既存の内部診断API利用者は管理者認証と新しいURLへ移行する。
## ストレージ暗号鍵と復旧（#6730）

接続設定の暗号鍵は `astack.secrets.key-base64` または `astack.secrets.key-file` で管理し、AI接続の鍵を共有する。DBと鍵のアクセス権とバックアップ先を分離する。初めて設定を暗号化して保存する際、鍵未設定なら鍵ファイルを生成するため、そのファイルを必ず保全する。起動時に保存済み暗号文の復号を読み取り専用で検証する。暗号化済みデータの復号では鍵を自動生成せず、鍵欠損・不一致時は起動を中断する。元の鍵を安全な場所から復元し再起動する。鍵を削除・差し替えて復旧しようとしない。DBだけでは復旧できない。

新規導入を前提とし、旧平文設定の一括移行処理は実施しない。暗号化済みDBと対応する鍵を同じ世代でバックアップ・復元する。サポート資料やチケットへ接続設定・鍵・復号結果を添付しない。

## ログイン試行制限の監視・回復（#6728）

Micrometer `astack.auth.login` の `outcome=admitted/throttled/success/failure` を集計する。IDやIP、パスワードをメトリクスラベル・ログに出さない。429比率・失敗率・CPU・DBロック待機を併せて確認する。制限は単一JVM内で保持し、再起動で解除される。複数インスタンスではそれぞれの上限が適用されるため、手前のプロキシ/WAFでも共有の制限を設ける。

通常は `Retry-After` の経過後に再試行する。拒否要求で待機は延長されず、窓の終了で回復する。攻撃が継続する場合は接続元をプロキシで遮断し、正常利用の回復を確認する。緊急解除が必要なら原因を除いた後にインスタンスを再起動する。利用規模に応じた上限調整は上記設定で行い、設定変更後に再起動する。実測の負荷閾値や本番DoS耐性を保証する値ではない。
## 依存脆弱性の再監査

バックエンド依存は [2026-10-26監査記録](../security/backend-dependencies-20261026/README.md) の手順でMavenのruntime解決結果をOSVへ再照会する。バージョン一致を悪用実証と扱わず、残件の機能利用条件を照合する。新たなSSEフラグメント・WebFlux route・XSLT view・MCPサーバ導入時は記録した非到達性の判断を再評価する。

## 公開・配信とリバースプロキシ連携

「元文書」には取込元と除外対象を置く。「公開・配信」へ内部/外部Webサーバの選択、公開URL、外部保存先、外部APIパスを集約する。メニューURLは「閲覧・権限」に配置する。内部公開のAPI接続先は自動設定し、入力欄を表示しない。

「リバースプロキシと連携する」（`pathConfig.apiProxyEnabled`）は内部/外部共通の任意設定。有効時のみ信頼するプロキシIPと「アクセス履歴にユーザー名を記録する」を表示し、ユーザー名の記録を有効にした場合だけヘッダー名を表示する。信頼するIP/CIDRは連携中の公開APIの接続元を制限する。公開コンテンツへの直接アクセス遮断と前段の認証はネットワーク/プロキシ側で設定する。この連携はAstackのログイン・文書ACLを代替しない。

新規の連携設定はOFF。旧設定に明示値がなければ、外部公開で有効だった接続元制限だけを継承し、内部公開で無視していた旧フラグは有効化しない。明示値があれば配信先と独立してその値を使用する。連携OFFでは保持したIP/ヘッダー設定を検証・適用せず、ユーザー名記録OFFでは保持したヘッダー名を検証・使用しない。有効/無効の変更後はTEMPLATEビルドで配布ページへ反映する。

## ライブラリ設定の分類

ライブラリ編集の左メニューは「基本情報」「元文書」「変換・ビルド」「公開・配信」「閲覧・権限」「検索」「AI処理」の7分類とする。設定の保存先キー・値・権限制御・依存条件は維持する。

| 分類 | 内容 |
| --- | --- |
| 基本情報 | プロジェクト、ライブラリ名、タイトル |
| 元文書 | 接続先、取込パス、除外パス、除外拡張子 |
| 変換・ビルド | 変換方法、更新確認、プロファイル、パラメータ、ビルド前後の処理、処理ログ |
| 公開・配信 | 連携/独立配信、内部/外部サーバ、公開URL・保存先・API・リバプロ、配置方式、未対応形式・変換失敗時の扱い |
| 閲覧・権限 | テンプレート・ビューア、メニューURL、更新マーク、共有・アクセス履歴、原本取得・操作許可・アクセス権継承 |
| 検索 | 検索方式・対象・外部検索接続先 |
| AI処理 | 共通モデル、要約、タグ、メタ情報、ベクトル |

「閲覧・権限」は画面表示、共有・アクセス履歴、操作と権限に分ける。アクセス履歴は利用者の閲覧・操作の記録とし、変換・ビルドの処理ログと区別する。除外拡張子は旧「文字列除外」の表示名を整理したもので、拡張子による判定と保存キーは変更しない。
